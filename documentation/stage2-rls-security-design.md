# Stage 2 — RLS and Security Design

> **Stage 2.1 update.** This design has been reviewed table by table in `stage2.1-security-review.md`: **13 policies amended, 112 unchanged, 2 tables removed (MRN merged into GRN), 11 new tables given policies, 21 findings with fixes.** Notable changes: every view uses `security_invoker`; a **restrictive active-user policy** is added to every table; default privileges are revoked; audit JSON is hidden from depot roles (`v_audit_summary`); notifications cannot target the Tyre Man role; Central Store tyres are invisible to depots until an allocation is approved; withdrawal by an administrator is service-role only. Account administration is described in `stage2.1-employee-login-design.md`.

Design only. **No SQL has been executed.** The SQL snippets are illustrative drafts of what Stage 3 migrations will contain.

---

## 1. Principles

1. **Deny by default.** RLS is enabled (and `FORCE`d) on every table in `public`. A table with no policy is unreadable.
2. **The database decides, not the screen.** Role, depot, assignment and approval authority are all checked in policies or in `SECURITY DEFINER` functions.
3. **Reads by policy, writes by function.** Clients read through RLS-filtered `SELECT`. All status changes and master changes go through RPC functions. Direct `INSERT/UPDATE/DELETE` is granted only on draft content that the policy can fully validate.
4. **No deletes.** There is no `DELETE` policy on any table. Corrections are new rows or status changes.
5. **Least exposure.** Only `public` is exposed through the API; helper functions live in a private `app` schema; `anon` has no table privileges; the service-role key is never in the React bundle.
6. **Defence in depth.** Column privileges, `CHECK` constraints, triggers and RLS all agree; any one failing does not open a hole.

## 2. Authentication: Employee ID + Password on Supabase Auth

### 2.1 Mapping
Supabase Auth requires an email (or phone) identifier. Users enter **Employee ID** and **Password**; the app derives a deterministic synthetic email and signs in with the normal Auth API:

```
authEmail(employeeId) = lower(trim(employeeId)) + '@' + <AUTH_EMAIL_DOMAIN>
signInWithPassword({ email: authEmail(id), password })
```

- `AUTH_EMAIL_DOMAIN` is configuration (`VITE_AUTH_EMAIL_DOMAIN`), not a secret. The synthetic address is never shown and no mail is ever sent.
- Employee codes (`TIC-1147`, `HOT-0114`, `HOT-AE-021`) use only letters, digits and hyphens, so they form valid email local-parts.
- `auth.users.id` = `profiles.id`; `profiles.employee_id` → `employees` (unique). Access always derives from `employees.role_code` / `org_unit_id`.
- **Passwords exist only in `auth.users`** (hashed by Supabase Auth). They are never stored in application tables, the frontend, the repo, or logs.
- Generic failure message ("Employee ID or password is incorrect") so the login does not reveal which part failed. Supabase's built-in rate limits apply.

### 2.2 Account creation (no public registration)
- In the Supabase dashboard: **disable "Allow new users to sign up"** (and the email provider's sign-up). Only the admin API can create users.
- A **local provisioning script** (run by you on your machine with the service-role key in an untracked file) calls `auth.admin.createUser({ email, password, email_confirm: true })`, then inserts the `profiles` row. It reads employees with `is_login_enabled = true`.
- Demo passwords are generated by the script and printed once, or read from an untracked local file; nothing is committed (UQ-12).
- Deactivating an employee (approved master change) sets `profiles.is_active = false` through a trigger and the script bans the auth user; helper functions return `NULL` for inactive profiles, so every policy fails closed.
- Password reset by email does not work with synthetic addresses; resets are done by the administrator script (UQ-11, UQ-12).

### 2.3 Role routing
After sign-in the app calls `rpc('my_session')` which returns `{ employee_code, full_name, role_code, org_unit_id, org_unit_name }`. Routing is driven by that response and by RLS-protected data only. There is **no role selector**; a hand-edited role in the browser changes nothing because every query is re-checked in the database.

### 2.4 Feasibility
| Check | Result |
|---|---|
| Supabase Auth can sign in with a synthetic email + password | Yes — standard `signInWithPassword` |
| Users can be created without sign-up and without email confirmation | Yes — admin API `createUser` with `email_confirm: true`, sign-ups disabled |
| Role cannot be forged client-side | Yes — role is not read from JWT `user_metadata` (which users can edit); it is read from `employees` in the database |
| Passwords never in app DB / frontend | Yes |
| **Open point (not yet tested):** whether Supabase's email validator accepts the chosen synthetic domain | **Untested.** No Supabase action has been taken in Stage 2. Stage 3 begins with a one-user spike. If the domain is rejected, the fallback is a domain you control (UQ-12). |

### 2.5 Optional later hardening
Custom access-token hook adding `role`/`org_unit_id` claims for faster policy checks (role changes then apply at next token refresh) — not needed initially; MFA for HO/AM.

## 3. Helper functions (schema `app`, `SECURITY DEFINER`, `STABLE`, `search_path = ''`)

```sql
-- draft, illustrative
create function app.current_employee_id() returns uuid
language sql stable security definer set search_path = '' as $$
  select p.employee_id from public.profiles p
  where p.id = auth.uid() and p.is_active
$$;

create function app.current_role() returns public.role_code
language sql stable security definer set search_path = '' as $$
  select e.role_code from public.employees e
  where e.id = app.current_employee_id() and e.status = 'ACTIVE'
$$;

create function app.current_depot_id() returns uuid
language sql stable security definer set search_path = '' as $$
  select e.org_unit_id from public.employees e where e.id = app.current_employee_id()
$$;

create function app.visible_depot_ids() returns setof uuid
language sql stable security definer set search_path = '' as $$
  select u.id from public.org_units u where app.current_role() in ('HO','AM')
  union select app.current_depot_id()
  union select a.org_unit_id from public.user_depot_access a where a.profile_id = auth.uid()
$$;

create function app.has_capability(cap text) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.role_capabilities c
                 where c.role_code = app.current_role() and c.capability = cap
                   and c.is_enabled and c.is_resolved)
$$;
```
Policies call `(select app.current_role())` so Postgres evaluates it once per statement (init-plan caching). `EXECUTE` is revoked from `public` and `anon` and granted to `authenticated` only where needed.

## 4. Policy classes

| Class | Pattern | Typical SELECT | Typical write |
|---|---|---|---|
| **G1** Global reference, all roles | read-only reference | any active user | none (apply functions only) |
| **G2** Global reference, staff only | as G1 but not Tyre Man | role in HO, AM, SUP, TIC | none |
| **G3** HO/AM only | admin-level reference | role in HO, AM | none |
| **D1** Depot-owned document | owner depot | `org_unit_id in visible_depot_ids()` | Tyre IC insert/update **drafts** in own depot; status via RPC |
| **D2** Cross-depot document | owner **or** addressed unit | owner depot or `request_to` / `to_org_unit` in visible set | owner depot only; counterpart actions via RPC |
| **D3** Depot operational record (non-document) | owner depot | visible depots | Tyre IC (capability) in own depot |
| **T1** Task-assigned (Tyre Man) | own tasks | Tyre Man: `assigned_employee_id = me`; Tyre IC/SUP: own depot; HO/AM: all | Tyre Man: only execution tables of own tasks, only while task status allows |
| **C1** Child of a parent | inherits | `exists (select 1 from parent where parent visible)` | same as parent, only while parent is editable |
| **A1** Append-only history | inherits | visible if parent visible | insert via function only; update/delete blocked by trigger |
| **M1** Master approval engine | maker / checker | HO: all requests; AM: all requests; others none | functions only |
| **S1** Self-service | own row | `id = auth.uid()` | column-limited |
| **N1** Notifications | recipient | targeted to me, my role+depot, or broadcast | `notification_reads` insert for self |
| **X1** Administrator only | system config | limited read (see table) | none for clients |

if v_req.maker_id = auth.uid() then raise exception 'maker cannot approve own request'; end if;

## 6. Storage (photos)
- Private bucket `job-photos`. Object path `{org_unit_id}/{job_task_id}/{uuid}.jpg`.
- Upload policy: a Tyre Man may insert only into a folder for a task currently assigned to them; Tyre IC for tasks in their depot. Read: same parties plus HO/AM. Size ≤ 5 MB, MIME in (image/jpeg, image/png, image/webp) enforced by bucket settings and an `attachments` row.
- No public bucket and no public URLs; signed URLs for display.

## 7. RPC / function security rules
1. All write RPCs are `SECURITY DEFINER` with fixed `search_path = ''`, fully-qualified names, and an explicit first-line role/depot/status check.
2. `REVOKE EXECUTE ... FROM PUBLIC, anon;` then grant to `authenticated`.
3. Functions never trust parameters for identity: actor = `auth.uid()`; depot is read from the target row and compared with `visible_depot_ids()`.
4. All approvals consult `approval_routes` (operational) or require `AM` (master). Unresolved routes (`approver_role` null) raise "workflow not yet configured".
5. Remarks guard: `if length(btrim(coalesce(p_remarks,''))) = 0 then raise ...`.
6. Every function writes `audit_logs` and the relevant history table in the same transaction.

## 8. Edge Functions
None are required for core functionality. The design avoids them to keep everything in Postgres and free-tier friendly. Optional later: a thumbnailer for photos, or a scheduled job (pg_cron if available, otherwise an on-demand function) for `schedule_instances` generation.

## 9. Secrets and configuration
- Browser bundle: only `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (publishable), `VITE_AUTH_EMAIL_DOMAIN`.
- Service-role key: only on the administrator's machine in an untracked file used by provisioning/seed scripts; never in Netlify front-end variables, never in the repo.
- `.env` in `.gitignore`; `.env.example` has placeholders only.
- Stage 9 check: grep the production bundle for the service-role key pattern and for the word `service_role`.

## 10. Threats considered
| Threat | Mitigation |
|---|---|
| User edits JWT / local storage to claim a different role | Role is never read from the client; policies call database helpers |
| Tyre Man guesses another job's id | Row filtered by `assigned_employee_id` |
| Tyre IC of depot A calls API with depot B id | `org_unit_id in visible_depot_ids()` fails |
| HO submits and approves own change | role + maker≠checker check |
| AM approves a change that makes their own account HO | cannot decide a change about themselves |
| Direct table update to skip approval | no write policies; column privileges exclude `status` |
| SQL injection in functions | parameterised, fixed search_path |
| History tampering | append-only triggers, no delete policy |
| Unauthorised signup | sign-ups disabled; `profiles` created only by script |
| Leaked anon key | harmless by itself: RLS denies everything without a valid user |
| Brute-force login | Supabase rate limits; generic error; optional MFA for HO/AM |

## 11. Test plan (Stage 3/4, before any UI depends on it)
SQL tests that impersonate each role (`set local role authenticated; set local "request.jwt.claims" = ...`) and assert for every table class:
- allowed rows visible, forbidden rows invisible (HO/AM all; SUP/TIC own depot; TM own tasks);
- direct `INSERT/UPDATE/DELETE` on masters fails for every role;
- HO cannot approve; AM cannot create; SUP cannot approve master changes; TIC cannot approve GIN;
- self-approval blocked; self-role change blocked; inactive employee locked out;
- missing remarks rejected for every reject/return/revert/cancel path;
- append-only tables reject updates; deleting anything fails.
Result matrix (role × table × operation) is committed with the tests.
